# dgpui 架构拆解：给零 GUI 背景工程师的通俗地图

这篇文章不预设你写过任何前端、Flutter 或游戏引擎，只用**系统编程和内存管理**的常识，把整个 GUI 框架拆开讲清楚。

---

## 核心难题：为什么 GUI 框架比命令行程序复杂？

写一个命令行工具，逻辑是**单向**的：输入 -> 处理 -> `print` -> 退出。

但 GUI 程序有三个绕不开的麻烦：
1. **它是反转的（Event-Driven）**：程序大部分时间在“睡觉”，操作系统随时发来“鼠标在 (40, 130) 点了一下”，你要反推它点中了你代码里的哪个按钮。
2. **屏幕位置是算出来的，不是写死的**：你写“卡片里有一段中文，宽度占满窗口”，窗口拉窄时文字折行变高，下面按钮的 `y` 坐标也得跟着往下移。
3. **内存和性能约束是矛盾的**：一秒可能重画 60 帧，如果每帧 `malloc/free` 几千个 UI 节点会很慢且碎片化；但有些数据（比如计数器 `count = 3`、输入框里的文字）又必须活过无数帧。

`dgpui` 的 6 个步骤，就是为了依次解决这三个麻烦。

---

## 一、两大内存世界：`FrameArena` vs `EntityStore`

这是理解 **GPUI 架构** 最关键的一刀——**把“长寿的数据”和“短命的界面描述”彻底分开**：

```text
+-----------------------------------+      +------------------------------------+
|       持久世界 (EntityStore)       |      |        瞬时世界 (FrameArena)        |
|                                   |      |                                    |
|  - 计数器状态: count = 3           |      |  - 本帧的 Div / Text 节点树        |
|  - 滚动偏移量: scroll_y = 120      |      |  - 算出来的矩形: x, y, w, h         |
|  - 观察者关系: view 订阅了 count   |      |  - 点击回调临时绑定的 Hitbox 列表   |
|  - 真正要执行的闭包/事件处理器       |      |  - DisplayList 绘制指令数组         |
|                                   |      |                                    |
|  生命周期：整个 App 运行期          |      |  生命周期：只有 1 帧！帧末一键清零！  |
+-----------------------------------+      +------------------------------------+
```

**一句话记住**：
- 业务状态放在 `EntityStore` 里，靠 `EntityId`（句柄 + `generation` 代数防悬垂）引用。
- 界面长什么样，每帧从 `FrameArena`（一个只往后拨指针的线性分配器）里快速 `alloc` 一整棵树，画完后 `arena.reset(.retain_capacity)` 一瞬间清空，**零 `free` 开销、零内存碎片**。
- **常见大坑**：正因为 `FrameArena` 每帧都会清空，**点击回调函数绝对不能捕获指向当前帧 `Div` 或临时字符串的指针**！回调必须只持有 `EntityId` 或持久状态。

## 二、六个 PR 模块逐一说明

### Step 1：窗口、事件循环与多后端抽象（`PlatformBackend` + `RendererBackend`）——已实现

物理像素用 `SDL_GetWindowSizeInPixels`，不要用逻辑尺寸乘 `SDL_GetWindowDisplayScale`。后者是“内容该放大多少”，在 Windows 200% 缩放时可以是 2，而窗口坐标本身已经是像素，乘上去会把交换链算成两倍大。像素密度（`SDL_GetWindowPixelDensity`）才是窗口坐标到像素的比值。详见 `docs/pr1-backend-and-window.md`。

- **解决什么问题**：GUI 框架的核心算法（布局、事件、状态）不应该直接 `import SDL` 或 `import Metal`。否则换个平台（比如 Linux 无窗口嵌入式 `DRM/KMS`、或者无头单元测试）就跑不动了。
- **怎么做**：
  - 定义两个接口（Zig 里的 struct + 函数指针 VTable，类似 Rust 的 `trait`）：
    - `PlatformBackend`：负责“等事件（休眠）、取窗口大小与 DPI 缩放比、切换鼠标光标、告诉系统需要重绘”。
    - `RendererBackend`：以后只接收框架产出的 `DisplayList` 和 `DamageRegion`。PR 1 实际收到的是 `FrameParams`（逻辑尺寸、缩放、清屏色、可选 `damage_rect`），并把它画到屏幕（或记到 Headless）上。
  - 提供两个实现：
    1. **`SdlBackend`**：用 SDL3 开窗口 + `SDL_GPU`（macOS 底层是 Metal），空闲时用 `SDL_WaitEvent` 挂起线程，CPU 占用 0%。
    2. **`HeadlessBackend`**：不弹窗口，把每帧收到的指令和事件记录下来，专门用于 `zig build test`。

### Step 2：渲染中间层（`DisplayList`）、脏区（`DamageRegion`）与 SDF 着色器——计划中，还没有代码

- **解决什么问题**：如果布局完直接调 GPU API，代码会耦合死，也没法做局部重绘和单元测试。
- **怎么做**：
  - **中间层 `DisplayList`**：把树拍平成一个按绘制顺序排好的数组：
    - `Quad`：矩形位置、填充色、圆角半径、边框宽度/颜色、阴影模糊半径。
    - `PushClip(rect)` / `PopClip`：裁剪区域栈（比如列表滚出框外要裁掉）。
    - `GlyphQuad`：贴字形小图用的矩形（Step 3 接入）。
  - **怎么用一个着色器画圆角 + 边框 + 阴影？（SDF 原理）**：
    - GPU 本质只会画三角形。两个三角形拼成一个矩形，在片元着色器（Fragment Shader）里，对每个像素算出它**离圆角矩形边缘的有向距离 `d`**：
      - `d < 0`：像素在里面 -> 画背景色；接近 `0` 的那一圈 -> 画边框色。
      - `d > 0`：像素在外面 -> 根据距离渐变透明（阴影），或完全透明（圆角被切掉）。
    - 再通过 **Instancing（实例化绘制）**：CPU 一次把 500 个矩形数据打包成一块缓冲区发给 GPU，**1 次 draw call 全部画完**。
  - **脏区 `DamageRegion`**：记录这一帧真正发生变化的矩形范围（并集），下发给渲染器做局部重绘或 Scissor 裁剪。

### Step 3：文字排版与字形图集（HarfBuzz + FreeType2 + `GlyphAtlas`）——计划中，还没有代码

- **解决什么问题**：GPU 不认识 `.ttf` 字体文件。而且一行字里可能有英文连字（`fi`）、中英文混排，每个字宽都不同。
- **三条流水线**：
  1. **Shaping（整形，HarfBuzz）**：输入 `"Hello 世界"`，输出每个字形在字体里的编号（`glyph_id`）和精确偏移量（`x_advance, x_offset, y_offset`）。
  2. **Rasterization（光栅化，FreeType2）**：把指定 `glyph_id` 按 **Retina 物理像素字号**（逻辑字号 × DPI 缩放）渲染成一张灰度小位图，防止高清屏文字发虚。
  3. **Atlas（字形图集，自写 Shelf 分配器）**：在 GPU 上开一张大纹理（比如 `1024×1024`），把常用的字形像拼图一样塞进去，记住 `(glyph_id, px_size) -> UV 坐标`。下次遇到同一个字，直接查表贴图，**一屏几千个字只需绑定同一张纹理、1 次 draw call 画完**。

### Step 4：链式 DSL 与手写 Flex 布局引擎——计划中，还没有代码

- **解决什么问题**：开发者不想手写 `x = 16, y = 48, w = 368...`。他们想写：
  ```zig
  div().flexCol().p(16).gap(8).child(text("标题"))
  ```
  框架必须自动算出每个盒子的精确矩形。
- **布局最核心的难点**：**高度往往取决于宽度**。
  - 当容器宽 400px 时，一段 20 个字的中文只占 1 行（高 24px）；当窗口被拖窄到 200px 时，文字必须折成 3 行（高 72px），下面的按钮必须自动下移。
- **怎么做**：
  - 手写一个精简但结构标准的 Flex 引擎（参考 Yoga/Taffy 的布局模型，不链接 Yoga 这个库）：
    1. 容器把可用宽度约束 `AvailableSpace`（定长 / 最大内容 / 无限制）往下传。
    2. 遇到叶子节点（文字），调用 **`measure_text(text, max_width)` 回调**，算出折行后的宽高。
    3. 容器根据 `flex_grow` / `flex_shrink` 分配剩余空间或压缩，最后根据 `justify_content` / `align_items` 确定绝对坐标 `(x, y)`。

### Step 5：持久状态 `EntityStore`、命中测试（Hitbox）与事件闭环——计划中，还没有代码

- **解决什么问题**：点击屏幕某个坐标 `(x, y)` 时，怎么找到对应组件、修改状态、并且只重绘受影响的视图？
- **怎么做**：
  1. **Paint 阶段顺便埋点**：画一个带 `onClick` 的按钮时，顺便把 `(rect, clip_rect, node_id, on_click)` 登记到当前帧的 `Hitbox` 列表里。
  2. **命中测试（Hit Testing）**：鼠标按下时，**倒序遍历** `Hitbox` 列表（后画的在最上层，盖住先画的），且坐标必须在 `clip_rect` 内。
  3. **事件冒泡（Bubbling）**：如果点中的是按钮里的文字，文字自己没注册 `onClick`，事件就沿着父节点往上传，直到遇到按钮触发回调。
  4. **状态通知（`notify / observe`）**：回调里通过 `EntityHandle` 修改 `count += 1` 并调用 `cx.notify(entity_id)`，框架把订阅了它的视图标记为脏，并请求下一帧重绘（同一轮事件里的多次修改合并成 1 次重绘）。

---

### Step 6：滚动、焦点输入与 `comptime` DSL 对比实验——计划中，还没有代码

- **解决什么问题**：
  1. 列表内容超出窗口高度怎么办？-> 滚轮事件改变 `Entity` 里的 `scroll_offset`，渲染时包一层 `PushClip(box)` 并整体平移子节点坐标。
  2. 键盘按键没有坐标，怎么知道输进哪个输入框？-> 维护 `focus_id`（焦点实体），点击输入框时切换焦点，键盘事件直接派发给当前焦点。
  3. **编译期 DSL vs 链式运行期 DSL**：用 Zig `comptime` 写一个小型声明式视图宏示例，直观对比：
     - **Chain Builder**（GPUI / `dgpui`）：运行期构造轻量树，类型推导直观，无需宏魔法。
     - **编译期宏/编译器**（Rust `proc-macro` / `.slint`）：编译期做语法转换或依赖分析（DAG），运行期连树结构都不用重建，但调试和动态结构复杂度高。
